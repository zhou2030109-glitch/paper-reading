# 证据边界：这篇论文真正证明了什么，没证明什么

定位提醒：这一节的目的**不是写审稿意见**，而是给用户一个"我可以信到哪一步"的刻度。语气要像学长提醒，不像 Reviewer 2。

## 1. 三类陈述永远分开

- 【作者声称】——abstract / intro / conclusion 里的话；
- 【实验能支持】——表和图里的数字实际能推到哪；
- 【我的推测】——合理但论文没测的（例如"在更长输入上大概会退化"）。

讲完一篇论文时，第 1 类和第 2 类的差集就是"没证明的部分"。

## 2. 相关性 vs 因果

性能提高不等于作者给的理论解释就是原因。常见情形：

- 方法同时改了三处，只给一个解释；
- 提升可能来自更多计算 / 更多数据 / 更强 backbone，而不是那个巧妙的模块；
- 消融掉了但没有控制变量。

## 3. Benchmark 过拟合的具体形态

- 方法针对固定测试规则或固定 evaluator 设计；
- evaluator 的偏好正好偏向作者方案（例如用 LLM 判分且判分模型同源）；
- 测试场景过于理想化（输入干净、工具不失败、环境静态）；
- 闭集 / 小规模任务被包装成通用能力；
- 训练集与测试集共享模板或共享生成器。

## 4. 平均分掩盖了什么

问：平均分之下，最差的 10% 是什么样？少数类、OOD、长尾、大规模输入、长时任务、最困难子集是否单独报告？

若只给了平均值，就明确说"这篇没有回答极端情况下的表现"。

## 5. 现实假设过强清单

逐条对照论文默认了哪些前提：

- 输入完全正确、需求完整明确；
- 数据永远可访问、格式永远规范；
- 环境不变化、工具不会失败、API 不会超时；
- 标注无噪声；
- 计算资源充足；
- 评测者永远公正。

去掉其中任一条，方法还成立吗？这个问题的答案就是"下一步能研究什么"。

## 6. 常见的包装手法（要能识别，但表述要克制）

- 把工程集成（接了几个工具、加了 Agent 循环）说成方法创新；
- 换一个更容易的评测口径得到"大幅提升"；
- 只在自建 benchmark 上对比；
- 用"我们首次提出"包装已有概念的一个变体；
- 把 limitation 写成"未来工作"来淡化。

指出时用事实句，不用评价句：不说"这是在灌水"，而说"这个提升来自更宽松的评测口径，不是方法本身"。
