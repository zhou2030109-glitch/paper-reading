# 流程、模块、公式、算法的讲法

## 1. 先把 pipeline 画出来

默认最重要的一步。用文字流程图，不要用散文描述流程：

```text
输入
 ↓
模块 A：做什么
 ↓
产生什么中间结果
 ↓
模块 B：做什么
 ↓
模块 C：做什么
 ↓
最终输出
```

**训练阶段与推理阶段必须分开画**，这是最常见的讲错点：

```text
训练阶段：
数据 → 构造监督信号 → 训练模型 → 得到参数

推理阶段：
新输入 → 模型预测 → 后处理 / 验证 → 最终结果
```

很多论文的"创新"只在训练阶段，推理时和 baseline 完全一样；也有反过来的。混着讲会让用户永远搞不清到底哪一步变了。

## 2. 每个模块必须回答的六个问题

1. 输入是什么（数据结构、来源）？
2. 输出是什么（数据结构，交给谁）？
3. 它解决什么问题？
4. 为什么不能省掉——**如果没有它，系统会在哪里坏掉**？
5. 作者为什么不用更简单的办法（规则、已有模块、直接拼 prompt）？
6. 它和前后模块是什么关系（串行 / 并行 / 反馈回路）？

只要第 4 问答不出来，就说明这个模块在本文里可能只是装饰，或者你还没读懂——两种都要如实告诉用户。

同时给一句"职责翻译"：不要写"A 模块负责特征提取"，要写"A 模块干的事是：把用户那句话里的硬约束（时间、预算、必须去的点）挑出来，变成后续求解器能直接用的结构化条件"。

## 3. 公式讲解顺序

遇到公式按这个顺序走，**先讲公式在系统里"干什么"，再讲公式本身**：

1. 这个公式想解决什么问题；
2. 输入是什么变量；
3. 输出是什么；
4. 每个关键符号代表什么（只讲关键的，不要逐个符号念）；
5. 直觉上它在做什么（一句话白话）；
6. 给一个具体小例子，把数字代进去；
7. 必要时再讲严格数学意义（为什么这样设计、和常见做法的差别）。

如果公式里有损失函数，额外说明：**它在奖励什么、惩罚什么**，这一条比数学形式更能让用户懂。

## 4. 算法 / 伪代码讲解顺序

1. 输入；2. 初始化；3. 每轮做什么；4. 判断条件；5. 如何停止；6. 输出；7. 时间 / 空间代价；8. 为什么优于朴素做法。

第 5 步经常被论文藏起来（迭代上限、早停、超时回退），但对复现和可信度影响很大，读到就主动指出。

## 5. 判断"真创新"的三层

始终记住：**论文"用了什么"不等于论文"创新在哪里"。**

| 层级 | 典型内容 | 份量 |
|---|---|---|
| 工程层 | 换模型、换 prompt、串并行调整、加一个简单模块 | 一般不算创新 |
| 方法层 | 新的训练方式、新的推理机制、新的优化目标、新结构、新的反馈或验证机制 | 是创新，看是否被消融支持 |
| 问题 / 范式层 | 定义了之前没被清晰提出的问题、改了任务设定、提出新系统范式、建立新 benchmark 或评价方式 | 最有份量 |

给结论时要落到具体一步：**"真正的创新是第 3 步那个把自然语言约束转成可验证条件的校验器，前面两步都是已有技术。"**

## 6. 一个可复用的讲法模板

> 以前是这么做的：……
> 这么做的问题是：……
> 作者观察到的关键点是：……
> 所以他加了一步：……（用一句白话）
> 这一步带来的差别是：……（有它 vs 没它）
> 形式上它叫：……（正式术语）
