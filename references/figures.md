# 图和表怎么讲

用户问"图 X 是什么意思"时，只讲那张图，不要顺手把整篇论文重讲一遍。

## 1. 第一句话：这张图想让你看懂什么

> **作者画这张图，是想让你看懂 / 证明 XXX。**

先给目的，再给内容。很多方法图的目的只是"说明整体架构"，不是"证明有效性"；结果图才是证明。两者不要混。

## 2. 第二句话：怎么读

明确告诉用户阅读顺序：

- 左 → 右（流水线）、上 → 下（分层/迭代）、中间 → 两边（中心模块 + 外围工具）；
- 实线 / 虚线 / 粗线各代表什么（数据流？控制流？可选项？反馈？）；
- 有没有颜色 / 阴影编码（通常是"作者新增的部分"）；
- 竖着的时间轴还是横着的阶段划分。

## 3. 每个框只讲一件事

不要逐字翻译图里的文字。对每个框回答：

> 这个框负责什么，它接收什么，又把什么交给下一个框。

## 4. 用具体样例把图跑一遍

这是最关键、也最容易被跳过的一步：

> 假设输入是 X（给出一个真实的、小的例子），它先进入 A，A 得到 Y，然后送给 B，B 做了 ……，最后输出 Z。

跑完之后用户才真正拥有这张图。图跑不通的地方，往往就是论文没讲清楚的接口，要指出来。

## 5. 最后指出真正贡献

明确区分：

> 哪些框是已有技术（可以直接标出它来自哪篇工作），哪一部分才是作者新增的。

## 6. 表格怎么读

- 先读表头：每一列是什么设定（数据集 / 模型规模 / 是否有外部资源）。
- 先看行是不是同类：不同 split、不同 evaluator 的数字**不能横向比较**。
- 加粗的通常是最好的，但要检查比较是否公平（见 data-and-experiments）。
- 注意缺格：表格里的"—"是"没做"还是"做不出来"，含义差别很大；论文没说的话就标明未明确。
- 结果表里同一方法出现多次（不同 backbone / 不同 shot）时，要说清楚差异来自设定还是来自方法。

## 7. 什么时候要说"这张图不能说明什么"

常见情况：

- 只有定性示例图，没有定量，不能用来支持泛化结论；
- 只画了成功案例，没有失败案例；
- 图里曲线只到某个规模，不能外推；
- 架构图里画了组件但正文没给消融，说明不了该组件有效。
