# 数据集与实验：判断一篇论文撑不撑得住

数据集不是背景信息，而是判断论文可信度的核心。

## 1. 数据从哪里来

先分类，再解释影响：

- 真实世界数据；
- 人工标注；
- 仿真 / 沙盒数据；
- 模板生成；
- 程序生成；
- LLM 合成；
- 多来源混合。

**合成数据、模板生成、LLM 生成的数据，很容易让任务"看起来很难、实际上分布很窄"**，这时要主动提醒用户。

## 2. 为什么这样构造

逐个回答：为什么不用真实数据？为什么需要 synthetic？为什么需要人工改写？为什么过滤掉一部分？为什么这样采样？

把构造动机和论文要证明的结论对上——**如果构造方式恰好绕开了难点，那结论就只能在这个分布内成立。**

## 3. 标注是否可靠

检查：标注者数量、是否专家、标注规范、是否计算一致性（kappa 等）、是否有仲裁机制、ground truth 是否本身带主观性。

涉及"逻辑正确性""是否合理""是否自然"这类判断时，要问：这条 ground truth 是人判的、规则判的，还是模型判的？谁判的，直接决定结论能有多硬。

## 4. Train / Dev / Test 是否真的独立

关注：是否随机划分；是否存在相似样本泄漏（同一模板、同一来源、同一时间窗）；是否只测 IID；是否测组合泛化；是否测 OOD；是否测长尾和极端情况。

**看到非常高的准确率时不要立即说"任务解决了"，先问：这个高分到底是在什么数据分布、什么评价标准下得到的？**

## 5. 实验流程先还原出来

```text
测试样本
 ↓
模型 / 系统运行
 ↓
生成结果
 ↓
Evaluator 判断
 ↓
计算 Metric
 ↓
与 Baseline 比较
```

注意 evaluator 是谁：规则、人、还是另一个 LLM？如果是 LLM 判分，要问是哪个模型、prompt 是否公开、是否与作者方案同源。

## 6. 每个指标解释四件事

1. 怎么算（一句话公式或口径）；
2. 高好还是低好；
3. 实际衡量什么；
4. **衡量不到什么**（第 4 条最容易被忽略，也最有价值）。

多指标时说明它们的分工与冲突，例如"主指标反映整体可执行率，但它对局部约束的违反不敏感，所以必须有第二个指标兜住"。

## 7. 比较是否公平

逐条检查：相同数据吗？相同 split 吗？相同 evaluator 吗？相同外部资源吗？baseline 是否充分调参？模型规模差距是否巨大？是否额外用了私有数据或工具？

> **不同 benchmark / split / evaluator 的数字不能直接横向比较。**

发现不公平时，不要直接说"作者作弊"，而是说"这个对比只在 X 条件下成立"。

## 8. Ablation 必读

看到消融要回答：

- 去掉了哪个模块；
- 指标掉多少（给出具体数值或百分比）；
- 是否证明该模块真的有贡献；
- 有没有模块几乎没有贡献（作者通常会说成"仍有提升"）；
- 是否存在多个模块同时变化，导致无法归因；
- 是否只做了"加"的消融，没做"换"的消融。

## 9. 需要主动补问的疑点

- 只展示平均分？（会掩盖极端失败、少数类、OOD、长尾、大规模输入、长时任务、最困难子集）
- 有没有失败案例、错误分析、人工评估？
- 是否报告了方差 / 多次运行 / 随机种子？
- 最大规模实验到了多少，能不能外推？
- 计算成本、推理延迟、token 花费是否报告？（"有效但贵 10 倍"是重要结论）
