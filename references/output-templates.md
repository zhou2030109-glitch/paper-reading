## 2. 裁剪模板

**"一句话"**：严格一句话，用"想解决……核心办法是……本质上是……"，不加任何补充。

**"一段话"**：一个自然段，包含 问题 → 老办法不行 → 新办法 → 结果 → 最大限制。

**"简单讲讲"**：四个小标题，每个 2~3 句
1. 为什么要做；2. 怎么做的；3. 结果如何；4. 最大局限。

**"讲一下流程"**：只画流程 + 逐模块讲输入输出。可以这样收尾：

> 整条链子的关键在 B：前面 A 做的事任何 baseline 都能做，只有 B 是把……变成……，这也是消融里掉分最多的模块。

**"图 X 什么意思"**：只说这张图（见 figures.md），最后一句说这张图**不能**说明什么。

## 3. 段落写法示例（对照用）

反面（禁止）：

> 作者采用 constrained decoding 和 Earley Parser。

正面：

> 模型生成内容时，不是想输出什么都可以，而是每一步都会先检查"按照规则，下一步哪些内容是合法的"，不合法的候选直接禁止。这类方法叫 constrained decoding，论文中具体用 Earley Parser 来完成规则检查。

## 4. 换讲法示例（用户说"没懂"时）

假设用户没懂"验证器"：

- 换法一（有无对比）：没有它的时候，规划器交上来的行程直接进评测，错了也照样算数；加了它之后，交卷前先跑一遍约束检查，不通过就打回去重写。
- 换法二（具体例子）：用户说"每天至少去一个博物馆"。没有验证器，模型可以把"每天"理解成"全程"，评测器还是会判它对，因为它只查关键词；有验证器就会逐天检查。
- 换法三（流程）：生成 → 提取约束 → 逐条核对 → 不通过则改写 → 再核对，最多 N 次。
- 然后回到术语：这一步在论文里叫 verifier-based feedback loop。

**要点：先让用户拿到一个具体场景，再把术语贴上去。**

## 5. 讲稿落盘

写文件时（`paper-notes/<slug>/notes.md`）用完整模板；**对话里只给裁剪后的版本**。不要把完整模板原样吐到对话里，用户会觉得啰嗦。
